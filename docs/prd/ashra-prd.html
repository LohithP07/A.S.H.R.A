Purpose of this document

This PRD defines what A.S.H.R.A is, what the first usable release must do, how it is allowed to behave with private data, and how the work is sequenced. It is written to be sufficient on its own: an engineer should be able to build from it, and the owner should be able to accept or reject the result against it.

It reflects decisions made during product discovery on 12–13 November 2026, including the choice of Gmail IMAP, Google Calendar read-only via private iCal, Telegram as the first control channel, a local task ledger, and a local model for sensitive content.

Section 1Executive summary

1Executive summary

A.S.H.R.A is a single-user, local-first assistant for Windows 11. It turns a stream of email, calendar events, tasks, and conversations into a small number of clear actions — and asks before it does anything that leaves the machine.

The project began as a 3D knowledge galaxy over markdown notes and a chat box. That foundation is complete and now serves as one surface of a larger product. The next release turns it into an assistant with a life model: who you know, what you owe, what is due, what is waiting, and what it has already done.

Version 1.0 is deliberately narrow. It reads Gmail over IMAP, reads Google Calendar through a private iCal address, keeps a local task ledger, drafts replies, produces a daily brief, and communicates through a Telegram bot with approval buttons. It does not send email, modify a calendar, move money, or touch health data without explicit, per-action approval. It does not read your personal Telegram chats, and it cannot place phone calls.

The problem

Personal administration is not hard because any single task is hard. It is hard because the inputs are scattered and the cost of switching is high. An ask arrives in email, a deadline sits in a calendar invite, a promise is made in a chat, and a bill is due on a date nobody wrote down. Existing assistants solve this by sending everything to a cloud service, which is exactly the trade the owner does not want to make.

The product bet

A small local model, paired with deterministic pipelines, is good enough for triage, extraction, summarisation, and short drafts. Complex planning and tool orchestration should not be delegated to a 2B–4B model. Instead, the system keeps a structured life model, uses rules for anything that must be exact, and uses the local model only where language understanding is genuinely required. Cloud models remain available for non-sensitive work.

Core promise

Nothing private leaves this machine, and nothing irreversible happens without a decision. Every read, draft, approval, and action is attributable, reviewable, and reversible where the underlying system allows it.

What v1.0 delivers

Inbox awareness

Read-only Gmail ingestion with thread reconstruction, local classification, ask extraction, and proposed tasks. Bodies stay on disk.

Calendar awareness

Private iCal ingestion, recurrence expansion, conflict detection, and free-slot search for scheduling suggestions.

Daily brief and follow-ups

A morning brief with today's events, three must-dos, waiting-on items, and one thing to ignore. Unanswered commitments are tracked.

Drafts with approval

Replies drafted in your voice, stored in a local outbox, and sent only after an explicit approval from the Desk or Telegram.

Phone control

A Telegram bot for briefs, commands, and one-tap approvals, restricted to an allowlisted chat with expiring nonces.

Life-model Galaxy

A world-model explorer over memories, people, projects, tasks, events, and sources. Works with zero notes.

What v1.0 withholds

Sending to new recipients, deleting mail, changing calendars, payments, purchases, health actions, smart-home control, arbitrary shell, and any reading of personal chat accounts are out of scope. So is multi-user support, macOS, Linux, and mobile native apps. The architecture leaves room for them; the release does not pretend to include them.

Delivery shape

Work proceeds in small, reviewable phases on named branches, each squash-merged after review. The connector foundation is complete; the immediate next step is the local model router, so that privacy rules are enforced before any real email is processed.

Section 2Product definition

2Product definition

What A.S.H.R.A is, what it refuses to be, and the principles that decide close calls.

2.1 Vision

A calm, private assistant that holds the administrative shape of a life — commitments, deadlines, people, and open loops — and reduces it to a short, honest answer: here is what needs you, and here is what I have already handled.

2.2 Problem statement

The owner runs a working life across email, a calendar, a browser, local files, and chat. The information needed to act is present but fragmented, and each fragment has a different interface. The result is recurring low-grade overhead: re-reading threads to find the ask, remembering promises made in passing, noticing a deadline only when it is close, and rebuilding context before every meeting.

Generic assistants reduce that overhead by centralising content in a vendor cloud. That solves the fragmentation problem by creating a privacy problem. A.S.H.R.A takes the opposite constraint as its starting point: the machine is the trust boundary. It must be useful without uploading mail, attachments, calendar detail, or contacts.

2.3 Design principles

#PrincipleConsequence
P1Local is the default, not a mode.Private content is processed locally. Cloud calls are an explicit exception with a visible reason.
P2Deterministic where correctness matters.Dates, recurrence, dedupe, routing, and permissions are code, not model output.
P3Propose, then act.Every external write has a reviewable proposal and an approval record.
P4Structure over screenshots.Prefer APIs, IMAP, iCal, and files. Use browser automation only when no structured path exists.
P5One brain, many workers.One orchestrator owns conversation and approval. Subagents are scoped and cannot act alone.
P6Show your evidence.Every claim links to the memory, message, or event that supports it.
P7Degrade honestly.No key, no model, no network, or no connector must produce a clear limitation, never a fabricated answer.
P8Small surface, sharp edges.Fewer tools, each with a narrow scope, an explicit schema, and a known blast radius.

2.4 Non-goals

  • Not a general chatbot. Chat is one interface to the life model, not the product's centre.
  • Not a multi-user or team product. One owner, one machine, one identity. No sharing, no tenancy, no admin console.
  • Not a cloud sync service. There is no A.S.H.R.A account and no vendor-side storage of private content.
  • Not an autonomous agent that acts unattended. Unattended work is limited to reads, local writes, and notifications to the owner.
  • Not a financial or medical advisor. Financial and health data are excluded from automation and model reasoning by policy.
  • Not a replacement for a calendar or mail client. It reads, summarises, drafts, and proposes; the native clients remain authoritative.

2.5 The user

Primary user — the owner

One technical Windows user who works across email, a browser, documents, and code. Comfortable with a terminal and a config file. Values privacy over convenience, but will not tolerate friction that repeats every day.

Secondary users — none

People who email or message the owner interact with drafts and replies, never with the assistant directly. They are never asked to install anything or create an account.

If the assistant cannot explain, in one line, what it did, on whose behalf, with what evidence, and under which approval, the feature is not ready.

Section 4User journeys

4User journeys

Six journeys define the daily product. Each one states what the user does, what the system does, and where approval sits.

4.1 Morning brief

StepActorBehaviour
1SchedulerAt the configured wake time, builds a brief from today's events, tasks, waiting-on items, and overnight email.
2Local modelRanks at most three must-dos and writes one line of context for each. No email body is quoted.
3TelegramDelivers the brief with buttons: Open Desk, Snooze 1h, Quiet today.
4UserReads on phone, taps through to the Desk for detail, or replies with a command.

Approval: none required. The brief is outbound to the owner only and contains summaries, never bodies or attachments.

4.2 Inbox triage to draft

StepActorBehaviour
1ConnectorFetches new mail with BODY.PEEK, so nothing is marked read. Stores headers and bodies locally.
2PipelineReconstructs threads, strips signatures and quotes, detects newsletters and receipts by rule.
3inbox_triagerClassifies each thread: reply needed, waiting, informational, or ignore. Extracts asks, people, and dates.
4SystemProposes tasks and memories. Creates nothing without confirmation, except explicit user requests.
5writerOn request or by rule, drafts a reply in the owner's voice. Saves it to the local outbox.
6UserReviews in the Desk, edits, then approves. Send is a separate, explicit action.

4.3 Promise capture

The user says or types: "Remember that I promised Sarah the deck by Tuesday." The assistant creates a task with person = Sarah, due = Tuesday, status = next, links the source message, and confirms in one line: "Captured: send Sarah the deck, due Tue 17 Nov." No further dialogue. If the date is ambiguous, it asks exactly one clarifying question.

4.4 Phone approval

StepActorBehaviour
1SystemPosts a draft summary to Telegram with Approve, Edit in Desk, Reject. The message carries a one-time nonce valid for 24 hours.
2UserTaps Approve.
3Approval serviceValidates chat allowlist, nonce, expiry, and current draft hash. Rejects stale or replayed taps.
4OperatorSends through SMTP. Writes an audit record with recipient count, draft hash, and approval id.
5TelegramConfirms: "Sent to Sarah (1 recipient)." The button is removed.

4.5 Scheduling a meeting

The user asks for thirty minutes with Sarah next week. calendar_scout reads the local calendar cache, finds three candidate slots that avoid conflicts and respect working hours, and scheduler drafts an invite as an .ics file plus an email draft. Nothing is sent and no event is created. The user approves, then either sends the draft or imports the .ics into Google Calendar.

4.6 File cleanup and app routines

StepActorBehaviour
1User"Clean up Downloads."

3DeskShows every move and rename. Deletions go to the Recycle Bin, never permanent.
4UserApproves the batch once. The operator executes and records each operation.
5SystemOffers to save the batch as a reusable routine with its own scope and approval policy.

4.7 End of day

An evening brief summarises what moved, what is still waiting, and what tomorrow looks like. It proposes up to three tasks for tomorrow and asks one question: "Anything to add before I close the day?" The answer is captured as a task or memory, and quiet hours begin.

5.3 Turn lifecycle

  1. Intake. A surface submits a request with an identity and a surface tag. Telegram requests must match the allowlisted chat.
  2. Classify. The router determines intent deterministically where possible. Only ambiguous intent reaches a model.
  3. Scope. The policy guard computes the maximum permission and the permitted model lane for this turn.
  4. Gather. Read tools and agents collect evidence. Every item carries a source reference and sensitivity.
  5. Produce. A produce agent writes text or a proposal. Output is validated against a schema before it is shown.
  6. Decide. If the turn implies an external write, the orchestrator creates an approval request with a payload hash.
  7. Act. On approval, a domain operator executes exactly the approved payload. The payload is immutable after approval.
  8. Record. The run, tokens, cost, evidence ids, approval id, and result are written to the audit log.

Architectural invariant

The orchestrator is the only component allowed to request approval, and domain operators are the only components allowed to execute external writes. No agent holds both capabilities.

Section 6Privacy and security model

6Privacy and security model

Privacy is not a setting. It is a set of classifications and gates that every request passes through before it reaches a model, a channel, or a tool.

6.1 Sensitivity classes

Classification is assigned at ingestion, inherited by derived records, and never downgraded automatically. A mixed request takes the highest class present. If classification is uncertain, the system chooses the more private class and says so.

6.2 Model lanes

Local lane

  • 2B–4B model through Ollama (qwen3.5:2b-q4_K_M default)
  • Email, calendar, contacts, tasks
  • Classification, extraction, summaries, short drafts
  • No network egress

Cloud lane

  • Configured provider, OpenAI-compatible
  • Public and non-sensitive internal content
  • Research, general planning, long-form writing
  • Explicit reason recorded per call

Refusal lane

  • Secret-class content
  • No model of any kind
  • Rules, search, and reminders only
  • Explains the policy to the user

F-3 — Model lane routing. The router may downgrade to local or refuse; it may never upgrade to cloud on failure.

F-4 — Approval state machine. Approved payloads are immutable; any edit returns the request to proposed.

An approval binds four things: the exact payload, the tool and its scope, the requesting surface, and an expiry. Telegram approvals also bind the chat id and a one-time nonce. Replays, stale hashes, and edits after approval are rejected and audited.

6.5 Prompt-injection defence

  • Email, calendar, web, and document content is data, not instruction. It is wrapped in an untrusted-content envelope before it reaches a model.
  • The policy guard scans for directive patterns — "ignore previous instructions", "send this to", "run this command" — and raises the risk score of the turn.
  • Tool selection is deterministic. A model may propose an action, but it cannot add tools, widen scope, or change recipients.
  • Links in messages are never fetched automatically. Fetching is a separate, visible step.
  • Any request in content to install software, send credentials, or contact a third party is surfaced to the user as a suspected injection.

Hard rule

If a request mixes secret-class content with anything else, the whole turn is refused. The assistant may say that it cannot help with that content and offer a manual path. It may not summarise, redact, or partially process it.

Section 7Connectors and channels

7Connectors and channels

A connector reads or writes one external system. A channel carries messages to or from the owner. Both declare their capabilities up front, and neither may exceed them.

7.1 Connector contract

Connector
  id            "gmail" | "gcal" | "files" | "browser"
  capabilities  { read, draft, write, delete }  // declared, enforced
  scopes        folders, domains, calendars, roots
  auth          credential_ref -> Windows Credential Manager
  poll()        incremental fetch, idempotent by external id
  normalise()   external record -> Source + Event + candidate Task
  health()      last success, last error, backlog, latency
  redact()      strip secrets and sensitive fields before logging

Every connector is idempotent, resumable, and rate-limited. Failures degrade to a visible status in the Desk; they never silently disable a capability.

7.2 Email — Gmail over IMAP

Transport

IMAP over TLS with a Gmail app password stored in the credential vault. SMTP over TLS is used only in the approved-send phase.

Read-only first

Fetch uses BODY.PEEK. No STORE, APPEND, EXPUNGE, label change, or move in the read phase.

Sync model

UIDVALIDITY plus UID cursor, stored per folder. A resync is a full pass; normal operation is incremental.

Scope

Inbox, plus an optional allowlist of labels. Sent mail is read only to learn voice and thread context, never quoted outward.

Message handling rules

  • Newsletters, receipts, and automated notifications are classified by deterministic rules, not by the model, and are excluded from the must-reply queue.
  • Attachments are stored locally with a content hash and never sent to a cloud service. Only text extracted locally may inform a draft.
  • Quoted history is collapsed before model input to reduce tokens and accidental disclosure.
  • Drafts are stored as structured records — recipient, subject, body, in-reply-to, attachments — so a send is reproducible and auditable.
  • An approved send binds the exact draft hash. Editing the draft invalidates the approval.
Authentication caveat

Gmail app passwords remain supported but are a legacy path. If Google retires them for this account, the fallback is Gmail API OAuth with restricted scopes. In OAuth Testing mode, refresh tokens expire about every seven days, which is why IMAP is preferred for v1.0. The connector interface isolates this change to one adapter.

7.4 Telegram — control channel

Telegram is the first channel because it is free, reliable on a phone, supports buttons and voice notes, and works with long polling so the local server never exposes a port. It is a control surface, not a data store.

Channel rules

  • Only the allowlisted chat id is accepted. Unknown chats are ignored and logged, never answered.
  • Approval buttons carry a nonce, an expiry, and the payload hash. A button can be used once.
  • Messages contain counts, times, and summaries. Email bodies, attachments, calendar titles with attendees, and contact details stay in the Desk.
  • Rate limits, deduplication, and quiet hours apply to every outbound message.
  • Every outbound message is recorded in the audit log with its template id and approval id, if any.
Limits to state plainly

A Telegram bot cannot read personal chats it is not part of, cannot place a voice call, and cannot send SMS. Real calls and SMS require a telephony provider such as Twilio and are deferred. Voice notes are a later addition with local speech-to-text.

7.5 Files and applications

The file operator works only inside declared roots — by default Downloads and a staging folder. It produces a dry-run plan before any change, moves deletions to the Recycle Bin, and records every operation. The app operator launches allowlisted executables and can arrange windows; it never types into an application unless a specific, approved routine declares the target and the text.

7.6 Browser

Browser automation uses Playwright with a dedicated profile, an allowlist of domains, and a visible session. It is used for research and for forms that have no API. It may fill fields and prepare a submission, but a submit, purchase, booking, or upload requires approval. Banking, health, and payment domains are blocked at the policy layer, not by prompt instruction.

7.7 Scripts

A script is registered in a manifest with a name, path, argument schema, timeout, expected output, and risk class. Running it requires approval per run unless a scoped grant exists. The runner captures stdout and stderr, truncates secrets, and records the exit code. Arbitrary shell from model output is never executed.

Section 8Memory, life model, and Galaxy

8Memory, life model, and Galaxy

Notes are a source. The life model is the product. The Galaxy is how you see it.

8.1 From notes to life model

The current build treats markdown notes as the centre of retrieval. That inverts the real dependency. Notes are one input among many, and the test notes currently in the repository are not a foundation. The life model must be useful with zero notes.

8.2 Memory lifecycle

  1. Propose. A capture proposal is created with text, type, sensitivity, confidence, and at least one source reference.
  2. Confirm. The user accepts, edits, or rejects. An explicit "remember that…" may confirm immediately.
  3. Store. The memory is written with an immutable id, a timestamp, and a provenance edge.
  4. Retrieve. Hybrid search: keyword, recency, type filter, and graph proximity. Sensitivity filters apply before ranking.
  5. Supersede. A newer memory can replace an older one without deleting history. Both remain auditable.
  6. Forget. The user can forget a memory; its source link is removed and the audit records the action, not the content.
Capture posture

The assistant proposes; the user confirms. The only shortcut is an explicit instruction to remember, which is treated as confirmation. Nothing is learned silently from email.

8.3 Galaxy as world-model explorer

The Galaxy stops being a map of markdown files and becomes a map of what the assistant knows and owes. It is a sense-making tool, not a task board. Dense task work belongs in Home and the Desk.

9.4 Reminders and recurrence

Reminders are generated locally and delivered through the active channel. Quiet hours suppress delivery until the next allowed window, except for a task explicitly marked urgent. Recurrence is expanded in code, not by the model, and completed instances are recorded so that a recurring task never double-fires.

9.5 Daily brief

The brief is a fixed template with variable content. It contains today's events with times, at most three must-dos, a waiting-on list, one item to ignore, and a single question. It is generated from structured data first; the local model only writes connective prose. If the model is unavailable, the brief still renders.

9.6 What is never automated

Money

No payments, transfers, purchases, or trading. Due-date reminders only.

Health

No medication, appointment, or medical-record actions. Reminders only, with no model involvement.

Irreversible destruction

Deletions go to the Recycle Bin. Permanent deletion requires a separate, explicit confirmation.

Identity and access

No password resets, account changes, or credential sharing.

Automation test

Before adding an automation, answer: what is the worst outcome if it runs while I am asleep? If the answer involves money, health, a third party, or permanent data loss, it is not an automation — it is a proposal.

10.4 Rules

  • One orchestrator. It owns the conversation, the approval request, and the final answer. Subagents are workers.
  • No irreversible action from a subagent. Execute agents act only on an approved payload supplied by the orchestrator.
  • Depth limit 2. An agent may call one level of helper and no further.
  • Budgets. Per-turn token, time, and tool-call caps. Exceeding a budget returns a partial result with a limitation note.
  • Shared memory. Only the memory curator proposes new memories. Agents read; they do not write.
  • Add on repetition. A new agent requires at least three repeated workflows, a distinct output schema, and a permission profile that differs from existing agents.

The default screen and the daily starting point. It shows the current brief, the Needs You queue, today's events, open tasks, and a capture bar. The queue is ordered by consequence and deadline, not by arrival time. Every item can be approved, snoozed, or opened in the Desk.

11.2 Desk

The control hub for work in flight. It contains the run timeline, the approvals queue, the outbox, connector health, and the audit log. It is the only place where a user can see exactly what the assistant did, with what evidence, and under which approval.

  • Runs: every turn, its agents, tools, tokens, cost, duration, and result.
  • Approvals: pending, approved, rejected, expired, revoked; payload preview and hash.

14.2 Reliability

  • The assistant starts and serves Home, Brain, tasks, and memory with no provider key, no Ollama, and no network.
  • Connector failures are isolated: one broken connector must not block the brief or the task ledger.
  • Every write is transactional. A failed send leaves the draft in failed, not sent.
  • Crash recovery resumes from the last committed cursor; no duplicate tasks or messages on restart.
  • A nightly backup copies the database and configuration to a local folder, excluding secrets.

14.3 Security

  • Server binds to 127.0.0.1 only. No CORS wildcard. No served path can reach config.json, data/, or the vault.
  • All external input is schema-validated and size-limited. Path traversal and symlink escape are rejected.
  • Approval payloads are immutable and hash-bound. Nonces are single-use and expire.
  • Logs redact secrets by key and pattern; a test asserts no credential value appears in any log line.
  • Dependency updates are pinned and reviewed; no post-install scripts from untrusted packages.

14.4 Usability

  • The daily loop — read brief, work queue, capture, close day — is completable without a manual.
  • Every error states what failed, what was preserved, and the next action.
  • Keyboard-first on desktop; every primary action reachable without a mouse.
  • No modal chains. No more than one decision per screen region.
  • Contrast meets WCAG AA; the UI remains legible at 125% scaling.

14.5 Maintainability

  • Typed Python with ruff and mypy in CI; tests for every connector and policy rule.
  • Connector and channel adapters are replaceable without touching the orchestrator.
  • Schema migrations are versioned, forward-only, and tested against a copy of real data shapes.
  • No feature depends on the test notes in notes/.

14.6 Accessibility and tone

The assistant speaks plainly, admits uncertainty, and never flatters. It uses short sentences, avoids exclamation marks in system messages, and states limitations before offering workarounds. Screen-reader labels are required on all controls, and the Galaxy has a list-view equivalent.

Definition of done

A requirement is done when it has a test, a visible surface, an audit event where relevant, and a line in the operator documentation. Code alone is not done.

  • Every phase ends with tests, documentation, and a short note in the implementation plan.
  • No phase may depend on a credential to be reviewable; fixtures and mocks are required.

15.4 Critical path

The critical path is 2E.0 → 2M → 2E.1 → 2F.0 → 2D → 2J → 2K → 2H. That sequence produces the daily loop: read mail locally, see approvals, approve from the phone, capture tasks, receive a brief. Approval hardening (2F.0) moves ahead of the Telegram channel and the outbox because both depend on a payload-bound, single-use approval. Everything else improves quality of life around that loop.

16.1 Risk review cadence

Risks are reviewed at each milestone exit. A risk that has not changed in two milestones is either accepted in writing or removed. A new critical risk pauses feature work until it has a mitigation.

Stop conditions

Stop and reassess if any of these occur: private content reaches a cloud provider; an external write executes without an approval record; a connector silently changes read state; or the daily loop takes longer than the manual alternative for two consecutive weeks.

B.1 Rules

  • config.json is gitignored and never served. The server rejects any request path that resolves to it.
  • A credential_ref is a name, not a value. The vault resolves it at call time.
  • The local lane is the default. Cloud is opt-in per sensitivity class, never per prompt.
  • Invalid or unknown keys fail startup with a precise message; the system does not guess.
  • Configuration is re-read per request where safe, so a model change does not require a restart.
